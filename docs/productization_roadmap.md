# MineShark 产品化路线图

## 1. 产品定位

MineShark 是面向安全分析人员的 AI 告警研判工作台。它不替代 Wazuh 的采集和告警能力，也不自动执行封禁；它负责把 MineShark 模型信号、Wazuh、Zeek、Suricata 和研判报告组织为可复核的处置证据。

核心问题不是“模型是否给出高分”，而是分析人员能否在一次告警处理过程中回答：

1. 这条告警是否需要升级处置？
2. 哪些证据支持或否定模型信号？
3. 谁做出了什么结论，依据是什么？
4. 该结论能否用于后续复盘和模型改进？

## 2. 第一条产品闭环

```text
实时 AI 告警
  -> 创建或关联研判案件
  -> 聚合网络与安全证据
  -> 分析员记录结论、负责人和理由
  -> 关闭或升级案件
  -> 汇总处置质量与误报反馈
```

第一阶段已经实现案件的创建、查看与决策持久化。案件保存原始告警快照，避免运行中的日志轮转后失去当时的研判依据。

## 3. 领域契约

### 案件

一个案件关联一个可追溯的 `alert_key` 和原始 `alert_snapshot`，并包含：

- `new`、`in_review`、`escalated`、`closed` 状态；
- `malicious`、`suspicious`、`benign` 研判结论；
- 负责人和文字化研判依据；
- 创建、更新时间和关闭时间。

案件不是模型预测的替代品。`benign` 表示分析员基于当前证据确认或暂定为误报，不能反向改写原始模型分数。

## 4. 后续优先级

### P0：持续接入与去重

轮询或增量读取实时告警源，为未处理告警创建案件，并用 `alert_key`、时间窗口和网络五元组避免重复建案。页面需要明确显示“新告警”“已有案件”和“已关闭案件”。

### P1：证据快照与可复现研判

将一次案件所见的 Wazuh、Zeek、Suricata 和 RAG 命中结果固化为版本化证据快照；报告必须引用快照而不是只在生成时临时查询日志。

### P2：处置质量度量

提供待研判时长、升级率、误报率、按模型阈值分桶的结论分布和数据源缺失率。这些指标用于发现流程问题和模型校准问题，不将少量演示样本包装成泛化性能。

### P3：运行可靠性

增加健康检查、任务超时与重试语义、审计日志、部署配置说明，以及演示数据与真实环境的明显隔离。

## 5. 验收标准

每项新功能至少满足以下标准：

1. 有一个明确的分析员动作和可观察结果。
2. 先以自动化测试定义行为，再编写实现。
3. 不要求真实密钥或生产日志即可用演示夹具验证。
4. 页面与 API 对同一领域对象使用一致字段与状态。
5. 完成后执行后端测试、静态检查、前端生产构建和浏览器交互验证。
